# ADR-005: Database Access, Migrations and Concurrency Control

**Status:** Accepted (2026-10-06). Revised the same day after review: capacity counted by
`refund_outcome`, fencing inside the locked transaction, test hook gated, `55P03`
handling, conflict-safe customer upsert, notes for `LISTEN/NOTIFY` and migrations.
Freeze review: lock order rule, `unknown` counted outside the window, bounded lock retries.
Final pass: schema list completed, capacity index, `ESCALATE` clears the lease.

**Locked 2026-10-06.** No further revisions; issues found from here on are fixed in code
and tests, or recorded in a new ADR that supersedes this one.

## Context
ADR-004's safety guarantees depend on specific database behaviors, so the access layer
must make them visible rather than hide them:

1. **Conditional updates whose row count you can read:** `UPDATE … WHERE claim_version =
   :v` returning 0 or 1 is the fencing check.
2. **Explicit transaction boundaries:** the policy check, the `APPROVED → EXECUTING` move
   and `first_send_started_at` commit together, or not at all.
3. **Two databases with separate credentials and migrations** (agent and refund-api).
4. **Async:** SSE streams (ADR-003) stay open for a long time.

### Async comes first, because it narrows the options
In a sync FastAPI app, each request runs in a thread from a pool, and an open SSE stream
holds its thread for its whole life. A few dozen pending-review subscribers could use up
the pool. In async code, a waiting stream costs almost nothing. Mixing (async for SSE,
sync elsewhere) means two drivers, two session styles, and blocking calls that stall the
event loop by accident. So the whole service is async.

Cost: Project 1's LLM layer is sync (`openai.OpenAI`) and mixed in with research-specific
code. Reuse becomes "extract the provider, retry and telemetry pieces and port them to
`AsyncOpenAI`", not a plain copy.

## Options Considered

### Option A: SQLAlchemy 2.0 Core (async) + Alembic + psycopg 3 — CHOSEN
- How it works: Tables are defined as Core `Table` objects. Queries are composable
  expressions (`update(runs).where(...)`) run on an `AsyncEngine`, with explicit
  transactions (`async with engine.begin()`). There's no ORM session, identity map or
  lazy loading. Alembic generates migrations from the Core metadata. The driver is
  psycopg 3 (`postgresql+psycopg`).
- Pros: Every ADR-004 requirement is visible in the code: `result.rowcount` is the
  fencing result, and the transaction is the `async with` block. Queries are composable,
  so policy queries with varying conditions aren't built from strings. No lazy loading
  means no async `MissingGreenlet` traps. psycopg 3 does both sync and async, so Alembic
  and scripts use the same driver as the app. Widely recognized.
- Cons: More verbose than an ORM for CRUD. Rows are mapped to Pydantic models by a small
  helper.
- Cost/latency/complexity profile: No runtime cost. Slightly more code for CRUD, which is
  cheap at this project's size.

### Option B: SQLAlchemy ORM / SQLModel — rejected
- How it works: Mapped classes, a session's unit of work, and relationships. SQLModel
  combines Pydantic models and table definitions.
- Pros: Less code for CRUD and relationships. SQLModel is popular in FastAPI tutorials.
- Cons: The unit of work decides **when** SQL runs (it flushes later). ADR-004 needs the
  opposite: "this update ran and affected 0 rows". The fencing update needs Core's
  `update()` anyway, so you'd run two styles side by side. Async lazy loading fails at
  runtime. SQLModel's shared API-and-table models tie the API contract to the schema, and
  it trails SQLAlchemy in features.
- Why we didn't use it here: It hides the exact behavior the safety design depends on.
- When it WOULD be the better choice: CRUD-heavy apps with deep relationships and few
  concurrency rules, like a CMS or an admin panel.

### Option C: Raw SQL (asyncpg / psycopg 3) + a migration tool — rejected
- How it works: Hand-written SQL strings, rows mapped by hand, and migrations as SQL
  files.
- Pros: The most control and the fastest; what runs is exactly what you wrote.
- Cons: No way to compose queries, so varying policy conditions push you toward string
  building. SQL typos show up only at runtime. No autogenerated migrations.
- Why we didn't use it here: Core gives the same visibility plus composability and typo
  protection.
- When it WOULD be the better choice: A small, performance-critical set of queries owned
  by people fluent in SQL.

### Option D: Async-native ORMs (Tortoise, Piccolo) — rejected
- How it works: ORMs designed for async from the start, with their own migration tools.
- Pros: Async-first, with Django-like ergonomics.
- Cons: Smaller ecosystems, no Alembic, weaker interview recognition, and the same
  unit-of-work opacity as B.
- Why we didn't use it here: Same visibility problem as B, with a smaller ecosystem.
- When it WOULD be the better choice: A team already standardized on one.

## Decision
**A: SQLAlchemy 2.0 Core, async everywhere, Alembic, psycopg 3.**

### Concurrency control: per-customer row lock (write skew)
Two runs for the same customer can each pass a per-user limit check at the same time.
Under Postgres's default READ COMMITTED isolation, both commit and the limit is exceeded.
This is write skew. The check transaction therefore:

1. `SET LOCAL lock_timeout = <config>`
2. `SELECT … FROM customers WHERE id = :user_id FOR UPDATE`. **Lock order rule: always
   `customers` first, then run rows**, in every transaction that takes both. No code path
   locks a run row and then a customer row. Heartbeats and claims touch only the run row
   and never take the customer lock, so no cycle, and no deadlock, is possible. The `customers`
   row is created the first time a Clerk user is seen with `INSERT … ON CONFLICT (id) DO
   NOTHING`, so two simultaneous first requests don't collide and the row always exists.
   The row is **only a lock target**: no other code path updates it (profile data lives
   elsewhere), so unrelated writes never contend with limit checks.
3. Computes used capacity: every `unknown` action, plus `confirmed` actions within the
   limit's window, excluding the action being evaluated (ADR-004, Source of truth). Run status is
   not used for counting.
4. Runs the policy check, then, **in the same transaction**, either:
   - moves the run `APPROVED → EXECUTING`, sets `first_send_started_at` and
     `refund_outcome = 'unknown'` with `UPDATE … WHERE id = :run AND claim_version = :v`.
     **If that update affects 0 rows, the worker has lost its claim: roll back everything
     and stop.** The move to `EXECUTING` **is** the reservation: once it commits, the next
     transaction for that customer sees the capacity as used.
   - or moves it to `ESCALATE` (same fencing condition), sets `escalated_at`, **clears
     `worker_id` and `lease_expires_at`** (a finished run holds no claim), and appends an
     `escalated` event for the customer, so the chat leaves "pending review" (ADR-003).
5. Commits, which releases the lock. **The lock is never held across the HTTP call.**

Rules:
- **Lock timeout:** only SQLSTATE **`55P03` (lock_not_available)** is treated as a lock
  wait. It rolls back; the run stays `APPROVED`; the worker keeps its claim, keeps
  heartbeating, and retries with backoff (ADR-004 step 7). It doesn't escalate, because
  waiting on a lock isn't a policy failure. Any other database error propagates and is
  handled as an error, never silently retried as a lock wait. **Lock retries are bounded:**
  after N consecutive `55P03` timeouts (config), the worker raises an error and an alert
  and releases its claim. The run stays `APPROVED` with nothing sent, so a later attempt is
  safe.
- **`AWAIT_APPROVAL` does not reserve capacity.** Proposals waiting for review are only
  proposals, and they shouldn't block the customer's other small refunds. As a result, an
  approved action can be rejected by the execution-time check if capacity was used in the
  meantime. That's the ADR-004 step 6 path (→ `ESCALATE`, nothing sent), and it's
  expected, not a bug. The reviewer console shows remaining capacity to make this rare.
- **Why a row lock over SERIALIZABLE:** SERIALIZABLE also prevents write skew, but it
  aborts transactions with errors that must be caught and retried, and the protection
  isn't visible in the code. The row lock is one line you can point at and test.

### Databases, roles and migrations
- Compose and CI: one Postgres container, two databases (`agent`, `refund_api`), two
  roles, created by an init script. The init script runs **`REVOKE CONNECT ON DATABASE …
  FROM PUBLIC`** on both databases and grants `CONNECT` only to each database's owning
  role. Postgres grants `CONNECT` to `PUBLIC` by default, so "no grants" alone means
  nothing.
- What this buys: separate **processes and credentials**, which is what ADR-004 relies on.
  It does **not** buy separate machines; both databases share a server locally.
- Two Alembic environments (`migrations/agent`, `migrations/refund_api`) and two
  `DATABASE_URL`s.
- Prepared statements are a config value (psycopg `prepare_threshold`), because Neon's
  pooled endpoint runs PgBouncer in transaction mode, where prepared statements have
  historically broken. The correct setting is verified against Neon's current docs in the
  deployment ADR.

### Schema conventions
- Money: `amount_minor BIGINT NOT NULL CHECK (amount_minor > 0)` plus `currency CHAR(3)`.
  No `NUMERIC`, no float (ADR-004 step 8).
- `runs` carries ADR-003/004's columns: `status`, `claim_version`, `worker_id`,
  `lease_expires_at`, `idempotency_key`, `first_send_started_at`, `last_attempt_at`,
  `escalated_at`, `review_deadline`, the canonical payload, `action_id`, and
  **`refund_outcome`** (`none | unknown | confirmed | rejected`, `NOT NULL DEFAULT
  'none'`, enforced as an enum or `CHECK`).
- **Capacity index:** a partial index on `(user_id, first_send_started_at) WHERE
  refund_outcome IN ('unknown', 'confirmed')`, so the limit query inside the locked
  transaction stays an index scan and the lock is held briefly.
- Status values are a Postgres enum or a `CHECK` constraint, never free text.

### Connection use
- **SSE streams don't hold pooled connections.** Each poll of the `events` table takes a
  connection and returns it right away. Otherwise async just moves the exhaustion
  problem from the thread pool to the DB pool, and Neon's connection limits are lower.
- Pool size is a config value, sized against the host's connection limit in the
  deployment ADR.
- **If ADR-003's polling is ever replaced by `LISTEN/NOTIFY`:** use **one** dedicated
  listener connection per process that fans out to all streams, never one per stream, or
  the exhaustion problem comes back. That connection must be direct (not pooled), because
  PgBouncer in transaction mode doesn't support `LISTEN`.

### Deferred to the deployment ADR
- Neon's current guidance on prepared statements behind its pooler.
- **Alembic runs over Neon's direct (non-pooled) connection**, not through PgBouncer.
- Pool sizes against the host's connection limits.

## Consequences
- **Tests run against real Postgres, never SQLite:** `FOR UPDATE`, row counts and
  isolation behave differently. CI already runs Postgres containers (ADR-004).
- **Race test with controlled timing:** a test hook pauses run 1 right after its capacity
  read. The hook only works when `DEBUG_FAULT_INJECTION=true`, and the service refuses to
  start with it set in production (same rule as ADR-004's `CRASH_POINT`). Run 2 starts, and the test waits until run 2 is either blocked on the lock (seen
  in `pg_locks`) or has passed its own read. Then run 1 is released. With the lock, the
  combined amount is over the limit and exactly one executes. **Negative control** with
  the lock removed: both execute. Relying on timing alone would make the negative control
  flaky, and a flaky negative control proves nothing.
- **Lock retry tests:** force a lock timeout → the run stays `APPROVED`, the claim is kept
  and it's retried; force N in a row → error, alert, claim released, nothing sent; force a
  different DB error → it is not retried as a lock wait.
- **Role isolation test:** the agent role can't connect to `refund_api`, and the reverse.
- **Migration checks in CI:** migrations are applied to an empty database, and `alembic
  check` fails if the table definitions and migrations drift apart. Autogenerated
  migrations are still reviewed by a person.
- **Project 1 reuse corrected:** the provider, retry and telemetry pieces are extracted
  and ported to `AsyncOpenAI`; research-specific code stays behind. See
  `KNOWN_TRADEOFFS.md`.
- **Platform note:** psycopg's async mode needs a selector event loop on Windows. Current
  development is on Linux (checked), and CI and containers are Linux. Anyone developing on
  Windows must set a selector event loop policy.
- **Revisit if:** CRUD-heavy features (admin screens) start to dominate. The ORM could be
  used just for those tables, while the run lifecycle stays in Core.

## Interview-ready summary
"I used SQLAlchemy Core with async psycopg 3 and Alembic, not the ORM, because my safety
design depends on seeing exactly what the database did. The fencing update returns a row
count I check, and the policy check, the move to EXECUTING and the first-send marker are
one explicit transaction. The ORM's unit of work decides when SQL runs, which is the
opposite of what I needed. The whole stack is async because open SSE streams would
otherwise use up a thread pool, and streams don't hold database connections either, or
the same problem just moves to the DB pool. Two runs for one customer could both pass a
limit check, a classic write-skew race, so the check transaction locks the customer row,
records the reservation by moving to EXECUTING before commit, and never holds the lock
across the HTTP call. I test it with controlled timing and a no-lock negative control.
SERIALIZABLE would also work, but it trades a visible lock for retry loops. An ORM would
be the right call for a CRUD-heavy app with few concurrency rules."
